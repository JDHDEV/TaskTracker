# worknotes — Claude Code project guide

Local-first Windows 11 desktop app: one person's work notes and tasks, with AI rewriting.
Stack: Tauri 2 shell · React 19 + TypeScript (Vite) · Rust core · SQLite via sqlx (runtime API) · FTS5 search.

## Read first
1. `docs/DESIGN.md` — the authoritative UI/behavior spec (tokens, layout, interactions, microcopy). Where the HTML prototype disagrees, DESIGN.md wins.
2. `docs/IMPLEMENTATION_PLAN.md` — the agreed roadmap. Work phases top to bottom; each has acceptance criteria.
3. `docs/reference/` — the interactive design prototype (`Worknotes_dc.html`, open in a browser) and the design tool's handoff notes.

## Architecture (do not bypass)
- The frontend never touches storage, AI vendors, or keys. It calls typed Tauri commands, and only through `src/lib/api.ts` — components never call `invoke()` directly.
- Two swap points, both Rust traits: `ItemRepository` (`src-tauri/src/db/mod.rs`) and `AiProvider` (`src-tauri/src/ai/mod.rs`). Commands depend on the `ProjectManager` (which holds loaded stores behind `Arc<dyn ItemRepository>`) and a provider registry — never on a concrete storage impl.
- **A project is a self-contained store in a user-chosen directory**, not a row in a shared DB. `ProjectManager` (`src-tauri/src/projects/mod.rs`) owns the loaded set (one `SqliteRepository` per loaded project), routes item writes to the right store, and fans reads (list/search/tags) out across loaded stores, k-way-merging the results so a merged list equals a single DB's. An app-level **catalog** (`catalog.db` in `app_data_dir`, its own migrator in `migrations_catalog/`) records every known project (UUID, name, directory path, loaded flag) and hosts the relocated `app_settings`.
- **The canonical store is one Markdown-with-frontmatter file per item** (`items/<uuid>.md`, git-mergeable, serialized/parsed by `src-tauri/src/store/itemfile.rs` — a hand-rolled, restricted, byte-deterministic format, no YAML dependency). The SQLite DB (`index.db`) is a **git-ignored, rebuildable index**, not the source of truth. Writes are **file-then-index** (the `.md` is written before the index row, so the git-tracked file is authoritative and a crash never leaves an index row with no file); load is **scan-then-rebuild** (the index is dropped and rebuilt from `items/*.md`, so a `git pull` that changed the files is picked up). Whole-file sync (OneDrive/Syncthing) and git-based merge are both supported; the manual **Reload** action re-reads files after an out-of-band change (a file watcher is deliberately deferred).
- Each repository impl owns its own SQL. SQLite uses FTS5 for search; a future Postgres impl would use `tsvector`. None of that may leak past the trait.
- `ProjectManager` is the single place that knows the app runs on SQLite + files; `src-tauri/src/lib.rs` `setup()` opens the catalog, runs the one-time legacy migration, and constructs the manager. Item reads always serve from the index; item writes always touch the canonical file first (`src-tauri/src/db/sqlite.rs` `items_dir` seam).

## Invariants (enforced in the repository layer — keep them there, not just in UI)
- The backend owns `id`, `createdAt`, `updatedAt`. `updatedAt` moves ONLY on content edits (title, body, status, priority, dueAt, tags, jiraUrl). Pin and archive flips never move it, and never reorder the list by recency. (An item does NOT carry a persisted `projectId` — its owning project is the store it lives in; the manager stamps the owning UUID onto every returned item. Items do not move between projects in v1.)
- `kind` is fixed at creation. Notes never carry status, priority, or dueAt — patches attempting it are silently ignored.
- List order: `pinned DESC`, then the sort mode, with `(created_at DESC, id ASC)` as the deterministic tiebreak — equal timestamps resolve by creation time, then by `id` (a UUID). This is creation-time order, NOT literal insertion order: `rowid` cannot be the tiebreak because rowids collide across per-project stores and are reassigned on any index rebuild, so a merged multi-store list would flap. `created_at` is minted at fixed millisecond precision, so the order is machine-independent and never flaps. The Rust k-way merge comparator (`pinned DESC`, sort-mode key, `created_at DESC`, `id ASC`) reproduces this exactly across loaded projects. Archived items are excluded from the default list AND from search.
- All search input goes through `fts_query()` (quoted prefix phrases). Never feed raw user text to `MATCH`.
- API keys live in the OS credential store (`keyring`). No command returns a key — `has_api_key` returns a boolean only. Saving an empty key deletes it.
- AI rewrites are proposals. Nothing replaces the **body** without an explicit user action (`Replace text`). Proposed **titles** are likewise accepted only via an explicit `Replace title` — with one carve-out: saving an item whose title is empty generates and auto-accepts a title as part of that explicit Save. That carve-out fills only an empty title (never overwrites a typed one) and never touches the body.
- Tag vocabulary is DERIVED, never stored: a tag exists while ≥1 non-archived item that is not a done task carries it **in a currently loaded project**. The vocabulary shown is the union across loaded projects (same name appears once; survives while any loaded carrier lives); unloading a project drops its exclusive tags. Do not add a tags table.
- Projects are per-directory stores identified by a UUID carried in a git-tracked `project.json` (with the index's `meta` table as a local fallback) — so a git clone keeps the project's identity even though `index.db` is git-ignored; without it, two clones on one machine would mint colliding identities and duplicate every item id. Path is an attribute the catalog reconciles on load — a moved file updates the path; a copy of an already-known UUID (recognized via `project.json`) is refused. A directory carrying a Stage-1 `project.db` and no `items/` is **upgraded in place on first load** (`migrate_db_to_files`): its rows are exported to `items/*.md`, a fresh `index.db` is built and **count-verified**, and the original is kept as `project.db.pre-stage2.bak` (never deleted) — the same count-verified, rollback-on-mismatch discipline as the one-time `notes.db` migration. A clone that brought only `items/*.md` (no `index.db`) has its index minted fresh on open. The three removal verbs: **Unload** (close the store, reversible), **Forget** (drop the catalog row, files untouched), **Delete files** (destructive; unloaded-first, confirm naming the absolute path, delete `index.db` + WAL sidecars + `items/` + any `project.db*`/`.bak` + the generated `.gitignore`, then the catalog row). Foreign/untrusted DB files are hardened against before migration (application_id marker, quick_check, schema allowlist, size cap, `trusted_schema=OFF`); item files are hardened too (filename derived only from the UUID id, per-file size cap, panic-free restricted parser, git-conflict-marker rejection with per-file partial success).
- Empty string clears optional text fields over IPC (`dueAt`, `jiraUrl`); omitted fields mean "unchanged". `NewItem.projectId` is REQUIRED (the create-target store); `UpdateItem` has no `projectId`.
- Settings and secrets never come from a project store: `app_settings` (JIRA config) lives ONLY in the catalog; keyring stays global; no key material is written near a project directory.

## Conventions
- IPC DTOs are serde camelCase. `src/types.ts` mirrors `src-tauri/src/models.rs` — change both or neither.
- Confirmation prompts go through `api.confirmDialog()` (the dialog plugin's async `ask()`), NEVER `window.confirm`/`window.alert` — the Tauri webview silently suppresses those, so a `window.confirm` guard would let every destructive action through unprompted.
- sqlx runtime API only (`query`, `query_as`, `QueryBuilder`). No `query!` compile-time macros; the build must never need a live `DATABASE_URL`.
- Schema changes are additive numbered migrations. Two migrators: `src-tauri/migrations/` (per-project index stores) and `src-tauri/migrations_catalog/` (the app catalog). sqlx applies them at open. Never edit an existing migration. Because `index.db` is rebuilt from `items/*.md` on every load, a schema change to the item store is compatible with existing data as long as `store/itemfile.rs` still parses the files.
- The canonical item file format (`store/itemfile.rs`) is byte-deterministic (fixed key order, LF, fixed-precision timestamps) so an unchanged item never produces a spurious git diff. It is parsed by a restricted line reader over the fixed field set — NOT a general YAML engine (no alias/anchor/deep-nesting DoS surface) — with a per-file size cap and no panics on file content. `project_id` is never written to a file (an item's owner is the store it lives in); no secret/keyring material is ever written to a file. If the field set changes, update BOTH the serializer and parser and keep the round-trip byte-identical (tests in `store/itemfile.rs` and `tests/export_import.rs`).
- Timestamps are RFC 3339 TEXT end to end (SQLite ↔ Rust ↔ JS), no mapping layers.
- Styling: CSS custom properties in `src/styles.css`, tokens per `docs/DESIGN.md`. Five named palettes are selected via `data-palette` on `<html>` alongside a polarity `data-theme` (`light`/`dark`), both set atomically; a palette swaps the neutrals **and** the accent/danger family (`--mark*`, `--danger`, and `--todo` all vary per palette). Only the doing/done status-dot colors are constant across all five. (Pre-Plan-11 this read "themes swap neutrals only; accents constant" — that rule is relaxed.)
- AI models are constants: `MODEL` in `src-tauri/src/ai/anthropic.rs` (`claude-sonnet-4-6`; current names at https://docs.claude.com/en/docs/about-claude/models/overview) and `src-tauri/src/ai/openai.rs` (`gpt-4o-mini`).

## Verify after every change
```
cd src-tauri && cargo test        # repository integration tests (in-memory SQLite, covers invariants above)
npx tsc --noEmit                  # strict typecheck (noUnusedLocals is on)
npm run build                     # production bundle must stay clean
npm run tauri dev                 # manual smoke test
```
Per-project store tests live in `src-tauri/tests/repo.rs` (in-memory SQLite); multi-store manager/lifecycle/hardening/upgrade/reload tests in `src-tauri/tests/project_manager.rs` (`tempfile` temp dirs); the canonical file format + git-merge fixtures in `src-tauri/tests/export_import.rs` and the `store::itemfile` unit tests; the legacy `notes.db` migration is tested inside `src-tauri/src/projects/legacy.rs`. New invariants get a test in the same commit.
