# Plan 17: AI review UX batch — instruction retention & history, auto-grow instruction box, confirm + highlight selection reworks, diff review card, unsaved-change visibility

**Created:** 2026-09-26
**Status:** Draft
**Planning Mode:** Subagent-Enhanced

**Summary**
- **Goal:** Make AI reworks reviewable and unsaved work visible across all three editors (items, prompts, scratch pads): keep the rewrite instruction in the box after a discard and, for prompts, record it in version history; grow the instruction box as the user types; confirm and visibly highlight selection reworks; show every proposal as a marked-up inline or side-by-side diff; and surface unsaved tabs on the rails and the three page tabs.
- **Approach:** Extract one shared presentational review card, add pure vitest-tested helpers (word-level Myers diff, instruction retention, dirty-tab sets, selection segments), keep all persistence to an additive optional `instruction` key on prompt version files plus one nullable index column, and land that irreversible on-disk change last.
- **Scope:** 35 implementation steps; 46 files (12 create, 34 modify) across 13 directories
- **Top risk:** The mirrored-backdrop selection highlight and the two-column diff card can only be verified by manual smoke testing (the repo has no DOM test harness), and feature 1b's `instruction` key is a permanent on-disk addition whose interpretation (provenance of accepted rewrites, not a recall list) is an assumption the owner must confirm before Phase 5.
- **Diagram:** [plan.17.diagram.html](plan.17.diagram.html) (threshold met: 46 files across 13 directories; new cross-module edges editors → `ReviewCard` / `SelectionBackdrop` / `rework.ts`, `ReviewCard` → `diff.ts`; Phase 0 must land before Phase 3, Phase 5 before Phase 6)

**Model Routing:** test-writer → opus (confidence medium, matched_rule R3); frontend-specialist → opus (confidence medium, matched_rule R3); no routes discarded, no injection suspected. architect, security-auditor, database-architect, tech-lead, adversarial-verifier and code-reviewer ran on their frontmatter defaults (routing never covers them).

## 1. Overview

Seven requests, all on the surface that plans 13–16 stabilised — the shared AI bar (`src/components/AiBar.tsx`), the three structurally identical body editors (`src/components/Editor.tsx`, `PromptEditor.tsx`, `ScratchEditor.tsx`), their highlighter-yellow review card, and the unsaved-changes signal:

1. **Prompt rewrite instruction history** — record the instruction behind each accepted AI rewrite of a *prompt* (the Prompts-page entity, which already has immutable per-version history with a `manual` / `aiEnhanced` provenance flag) and show it in the History dialog; and, in every editor, leave the instruction in the box when a rewrite is discarded instead of clearing it on submit as `AiBar.tsx:77` does today.
2. **Auto-expanding instruction input** — the single-line `<input className="aibar-custom">` becomes a one-row textarea that grows with its content.
3. **Confirmation before a selection rewrite** — a native confirm (`api.confirmDialog`) before a rework that targets a text selection, before any draft flush or IPC.
4. **Highlight the active selection during a rewrite** — the captured range stays visibly marked in the body textarea while its proposal is pending, even though the textarea loses focus when the user clicks the card.
5. **Side-by-side vertical diff view** — an option to review the proposal next to the original text in two columns.
6. **Highlight changes in proposals** — insertions and deletions marked between original and proposal.
7. **Highlight unsaved changes** — entity-level visibility of unsaved work beyond today's tab dot, editor frame and Save label: markers on rail rows and dirty-count badges on the Worknotes / Prompts / Scratch page tabs (unsaved work on a hidden page is invisible today).

Why it matters: the app's signature is "AI rewrites are proposals, never silent overwrites". Today the proposal card shows the new text alone, the instruction that produced it is gone the moment Rework is pressed, a selection rework gives no in-body cue of what is being rewritten, and unsaved edits on another page have no indicator at all. This batch closes those gaps without touching the AI backend or the item file format.

## 2. Strategic Assessment

*(Source: tech-lead agent; verified against code by the planner and the adversarial verifier.)*

- **Right set, wrong shape as written.** All seven cluster on one surface, so building them together is efficient — but the request treats a cheap frontend tweak and a permanent on-disk format change as one feature (1), and features 5 and 6 are one feature (a diff) with two layouts. The plan therefore **splits 1 into 1a (frontend retention) and 1b (persisted history)**, **merges 5 + 6 into one diff-review phase**, and puts **1b last** so the owner can still strike it after confirming the interpretation (§10).
- **Build once, not three times.** The review card is hand-copied in the three editors (`Editor.tsx:920-1004`, `PromptEditor.tsx:595-644`, `ScratchEditor.tsx:364-411`). Features 3, 4, 5, 6 and 1a all touch it. A **Phase 0 extraction of a presentational `ReviewCard`** (no behaviour change, its own smoke pass) is worth the up-front cost. A `useRework` hook is *not* — it would leak the item editor's title-generation phase and its shared `stopRef` (architect, §3).
- **Riskiest parts.** (a) Feature 4 has no platform primitive: a textarea's value is not DOM text, so the CSS Custom Highlight API cannot mark it and the native selection disappears on blur. The mirrored-backdrop overlay is the only viable technique and is verifiable only by hand. (b) Feature 1b is the one irreversible change: a new frontmatter key forever, plus an index column that four raw SQL INSERT strings and the move path must carry. (c) Diff colours must read on the yellow card in all five palettes.
- **Push-backs recorded, not adopted** (the request is explicit; §10 carries them for the owner): feature 3 adds a modal to a non-destructive action that the AI bar already labels ("Rework selection with", "N characters selected", "Whole text"); the rail-row half of feature 7 partly duplicates the existing tab dot, whereas the page badges fill a real gap.
- **Order:** cheap wins first (Phase 0, AI bar, unsaved badges), then the diff card, then the highlight, then 1b — the highest-uncertainty UI and the irreversible format change come last.

### 3.2 Storage facts for feature 1b *(database-architect; verifier claims 2–4)*

- Version files `prompts/<prompt-uuid>/<version-uuid>.md` are immutable and git-merge cleanly; `serialize_version` (`store/promptfile.rs:172-182`) writes `id`, `source`, `created_at`, `title` (quoted) in fixed order and **no schema marker** — `CURRENT_SCHEMA_VERSION` lives on the head `prompt.md` only (:56-59, :164). `quote()` (`store/itemfile.rs:466-481`) escapes `\\ " \n \r \t`, so a multi-line value stays on one physical line and can never form a `---` fence, a `key: value` line, or a conflict marker at a line start. `parse_frontmatter` (:456-490) puts every `key: value` into a map and `parse_version` (:214-239) reads only the four known keys — **unknown scalar keys are ignored by every shipped build**. Duplicate keys: last wins (:487). `title` uses `unquote(...)?` (:225-230) — a bad quote rejects the whole file; the new optional key must NOT copy that.
- **Index is rebuilt in rows, not dropped as a file** (verifier, claim 3): `open_store` reopens an existing `index.db` (`projects/mod.rs:1216-1218`), `rebuild_from_dir` deletes rows only (`db/sqlite.rs:351, :399-400`), migrations run at open (:233-236) and errors are scrubbed to "that project was created by a newer version of worknotes" (:1347-1355; test `project_manager.rs:990-1018`, run green). So migration 0009 makes v1.2.1 refuse any project the new build has opened until `index.db` (+ `-wal`/`-shm`) is deleted — the same accepted precedent as 0007/0008. `notes-app/CLAUDE.md:42` ("dropped/rebuilt") is inaccurate about the file and gets corrected in step 34.
- **Every place a version is built or inserted** — the field can only be dropped at a *raw SQL string*: `PromptVersionRecord` literals (compiler-checked once the field exists): `sqlite.rs:948` (import), `:1085` (create), `:1162` (update), `promptfile.rs:231` (parse), `:553` (test helper), `tests/export_import.rs:182`, `tests/project_manager.rs:2027, 2144, 2199, 2256, 2268, 2318, 2605, 2650`; `NewPrompt` literals (no `Default`): `tests/project_manager.rs:76`, `tests/drafts.rs:309`. Raw `INSERT INTO prompt_versions` strings (NOT compiler-checked): `sqlite.rs:442` (rebuild), `:974` (import/move), `:1113` (create), `:1188` (update). `PromptVersion` is built only by `FromRow` from the `versions()` SELECT at `:1213-1216`.
- **Move reads the index, not the files** (verifier, claim 2): `move_prompt` (`projects/mod.rs:814`) calls `source.versions()`, hands the DTOs to `target.import_prompt`, which rebuilds the target's canonical files from them (`sqlite.rs:948-956`) and verifies by **count only** (:835). A field absent from `PromptVersion` is silently stripped from the target's files; a field on the DTO but absent from the SELECT fails loudly (`ColumnNotFound`) because `PromptVersion` has no `#[sqlx(default)]` — which is why the plan forbids adding one.
- **`content_changed`** (`sqlite.rs:~1147`): an identical-content save appends no version, so an accepted proposal that equals the current body records no instruction. Accepted, documented (§10).
- **No length caps exist** for title, body or (today) the rewrite instruction; the only cap is `MAX_ITEM_FILE_BYTES` = 4 MiB (`itemfile.rs:34`) applied on **read/scan only** (verifier, claim 4 — SEC-1): `write_version`/`write_atomic` (`promptfile.rs:255-290`) and `write_item` (`itemfile.rs:305-315`) write any size; an oversized file is skipped on the next load with a UI warning (`sqlite.rs:343-348` → `App.tsx:876-881`, `ManageProjectsDialog.tsx:106-110`) and, for a prompt, the previous version becomes current. Only `scratchfile.rs:94` and `draftfile.rs:118` cap on write.
- `KNOWN_TABLES` / `KNOWN_TRIGGERS` (`sqlite.rs:41-49`) allow-list table and trigger names — a new **column** needs no allow-list change; a new table would.

## 5. Design

### Approach

Six feature phases plus docs, ordered cheap-and-safe → risky UI → irreversible format change:

- **Phase 0** extracts `ReviewCard` (presentational, no behaviour change) so the diff, toggle, notes and status text are written once.
- **Phase 1** rewires the AI bar (controlled instruction, auto-grow textarea, Enter/Shift+Enter/IME), adds per-editor request capture (`reworkRequest`), fixes the confirmed error-path leak of `selectionRework`, and adds the selection confirm — features 1a, 2, 3.
- **Phase 2** adds unsaved visibility (feature 7): pure `dirtyKeys`/`dirtyCount` helpers, page-tab badges fed by `onDirtyCountChange` from the two pages, rail-row markers, the tab accessible-name fix, and the `.btn-save` contrast fix.
- **Phase 3** is the diff review (features 5 + 6): pure `diff.ts` (Myers, capped), `reviewLayout.ts`, marks and the `Side by side` toggle inside `ReviewCard`.
- **Phase 4** is the selection highlight (feature 4): `SelectionBackdrop` behind the body textarea, shown only while the captured range is valid.
- **Phase 5 / 6** are feature 1b: backend (migration, models, file format, four INSERTs, caps, Rust tests, golden fixture) then frontend (types, accept path sends the captured instruction, History dialog shows it).
- **Phase 7** updates `docs/DESIGN.md` and `notes-app/CLAUDE.md`, and produces the owner's HTML smoke checklist.

Phases 2 and 5 are independent of 0/1 and may be worked in parallel; Phase 3 needs 0 and 1 (the card and `reworkRequest.original`); Phase 4 needs 1 (the error-path fix and `confirming`); Phase 6 needs 1 and 5.

### Architecture

- **Editors keep** `rework()` (stream, cancel, the item editor's R1 title phase), `discardProposal`, the accept handler (`spliceProposal` → `edit()` → `pendingCaretRef` → the editor's own `save(...)`, including PromptEditor's `source: "aiEnhanced"` + `instruction`), `stale`, `cardOpen`, the reseed resets, and their body `<textarea>` (placeholder, `data-menu-surface`, handlers).
- **`ReviewCard`** (new) owns the card markup, the diff memo, the layout toggle, the marks, the notes and the sr-only status line. It calls `onReplaceText` / `onDiscard` and renders an optional title slot (`children`) for the item editor.
- **`SelectionBackdrop`** (new) is a memoised mirror of `body` with a `<mark>` over `[start, end)`, rendered as a conditional sibling *before* the textarea inside a permanent `.body-wrap` wrapper (never wrap conditionally — that would remount the textarea and lose focus, undo, scroll and selection).
- **`AiBar`** becomes controlled for the instruction (`instruction` / `onInstructionChange`); the editors own the value, its reset on reseed, and the clear-on-accept rule.
- **Pure helpers** (all vitest-covered): `src/lib/rework.ts` (key handling, clear rule, confirm message), `src/lib/diff.ts` (tokenize, Myers, side projection, counts), `src/lib/reviewLayout.ts` (localStorage pref), `src/lib/openTabs.ts` (`dirtyKeys`, `dirtyCount`), `src/lib/selection.ts` (`selectionSegments`).
- **Backend (1b):** `instruction: Option<String>` on `PromptVersionRecord` → `PromptVersion` DTO → `types.ts`; one normalizer `promptfile::normalize_instruction(source, raw)` used by parse, serialize, create, update and import; migration `0009` adds the nullable column; the file is the source of truth, the index is rebuilt from it.
- **Dependency edges** (new unless marked existing): `Editor`/`PromptEditor`/`ScratchEditor` → `ReviewCard`; the same three → `SelectionBackdrop`; the same three → `src/lib/rework.ts`; the same three → `src/lib/api.ts` (existing; `confirmDialog` gains options); `ReviewCard` → `src/lib/diff.ts`; `ReviewCard` → `src/lib/reviewLayout.ts`; `SelectionBackdrop` → `src/lib/selection.ts`; `App` → `PromptsPage`, `App` → `ScratchPage` (existing; new `onDirtyCountChange`); `App` → `ItemList`, `PromptsPage` → `PromptList` (existing; new `dirtyKeys`); `App`/`PromptsPage`/`ScratchPage` → `src/lib/openTabs.ts` (existing; new helpers); `PromptHistoryDialog` → `src/types.ts` (existing; new field); `src-tauri/src/db/sqlite.rs` → `src-tauri/migrations/0009_*.sql`; `src-tauri/src/db/sqlite.rs` → `store/promptfile.rs` (existing; new field); `src/types.ts` ↔ `src-tauri/src/models.rs` (existing mirror); `src-tauri/tests/*` → `src-tauri/src/*` (existing).

The change map is drawn in [plan.17.diagram.html](plan.17.diagram.html) (illustrative; this file is authoritative).

### Key Decisions

- **D1 — Presentational `ReviewCard`, no `useRework` hook.** Rejected: no extraction (about 80 lines of diff/toggle/notes written three times, three cards drifting); a hook (leaks the item editor's title phase and shared `stopRef`; each editor's reseed would still reset its own state).
- **D2 — Controlled AiBar instruction; `<textarea rows={1}>` with CSS `field-sizing: content` + `max-height`; Enter submits unless Shift is held or `e.nativeEvent.isComposing || e.keyCode === 229`; `readOnly` + `aria-disabled` while busy (not `disabled`, which dumps focus to `<body>` on submit); `aria-label="Rework instruction"`; preset chips still fill the box (`DESIGN.md:77`) and move focus into it.** Rejected: a `resetSignal` prop (cannot express "clear only if unchanged"); a scrollHeight resize loop (synchronous layout read per keystroke); giving the box its own full-width line (a layout change DESIGN.md does not describe). **Amended in execution (§12 F14):** the box is NOT read-only while busy — the item editor's title phase keeps `busy` true after the stream and a read-only box dropped keystrokes; Enter stays blocked while busy and the request keeps its captured instruction, so editability costs nothing.
- **D3 — Retention rule:** the instruction stays in the box after Rework; it is cleared only when `Replace text` succeeds **and** the box still equals the instruction that was sent (`shouldClearInstruction`); Discard, cancel, stale-refusal and errors leave it. Rejected: clearing on accept unconditionally (wipes a new instruction typed while the proposal was pending).
- **D4 — Request capture:** one new state per editor, `reworkRequest: { original: string; instruction: string } | null`, set in `rework()` (`original = sel ? sel.text : body`) and cleared everywhere `selectionRework` is cleared **plus in the stream-error catch, which also clears `selectionRework`** (the confirmed defect). The instruction persisted by 1b comes from here, never from the box (R-8). Rejected: reshaping `selectionRework` across its twelve sites.
- **D5 — Confirm (feature 3), selection mode only, in this order:** `captureSelection` → set `confirming` + `selectionRework` (so the highlight shows during the dialog) → `await api.confirmDialog(message, { okLabel: "Rework selection", cancelLabel: "Cancel", kind: "info" })` → Cancel: clear both, return (no flush, no IPC, box untouched) → OK: re-check `isSelectionStale(liveBody, sel)`; if stale, keyed toast `The selected text changed — select it again.` and return → `draftBackup.flushNow()` → stream. Guarded by `confirmingRef` (a queued second Enter must not open two dialogs): set together with `setConfirming(true)` at entry and **reset on every exit path** — Cancel, the stale-abort, a thrown dialog error, and the normal continuation before the flush — via `try { … } finally { confirmingRef.current = false; setConfirming(false); }`; a guard left set would silently disable every later selection rework in that editor. Message: `Rework only the N selected characters?` + optional second line `Instruction: "<first 80 chars>"`; never the selected text (R-7). `api.confirmDialog`'s second parameter changes from `title` to an options object `{ title?, okLabel?, cancelLabel?, kind? }` (title still defaults to `"worknotes"`); all 17 existing call sites pass only the message, so nothing else changes. Rejected: `window.confirm` (suppressed by the webview); confirming after the flush (a cancel would still write a draft snapshot); a "don't ask again" toggle (the native `ask` has none; a Settings switch is deferred, §10). **Amended in execution (§12 F5):** the pseudocode's `setSelectionRework(sel)` before the await was a race — it clobbered an already-open selection card. As built, the confirm-time highlight uses a separate `confirmingSel` state and `selectionRework` is set only where a confirmed rework supersedes proposal + range + request together.
- **D6 — Selection highlight = mirrored backdrop.** Permanent `.body-wrap` (position relative, carries `--surface` + radius, **no** `overflow: hidden` — it would clip the focus ring); textarea `background: transparent` only while highlighting; backdrop `position: absolute; inset: 0; pointer-events: none; user-select: none; overflow: hidden; color: transparent` matching `.body`'s box-sizing, 1px transparent border, `padding: 14px`, font 15px / line-height 1.6, `white-space: pre-wrap; overflow-wrap: break-word; word-break: normal; tab-size`; **both** elements `scrollbar-gutter: stable` (measured `padding-right` via `ResizeObserver` is the fallback if parity fails in the smoke test); a trailing `\n` gets a `\u200b` sentinel so scroll heights match; `onScroll` writes `hl.scrollTop = ta.scrollTop` directly; `useLayoutEffect` syncs on mount; `<mark>` = `--hl-fill` background + 2px underline (`--mark-ink` light / `--mark` dark) because the light fills are only 1.07–1.15:1 against the surface (WCAG 1.4.11 / 1.4.1); `@media (forced-colors: active)` keeps the glyphs transparent and uses `Mark`. Shown only while `selectionRework !== null && !stale && (confirming || proposal !== null)`; when the range goes stale it disappears (it never relocates — plan 13 D4) and the card's status line announces the existing `The selected text changed…` message. Rejected: contenteditable / an editor library (breaks undo, line clipboard, paste, spellcheck, the native menu surface); read-only body during a pending proposal (contradicts D4); CSS Custom Highlight API (cannot target textarea contents).
- **D7 — In-house word-level Myers diff (`src/lib/diff.ts`), no dependency.** Tokenizer `/\r\n|\n|[^\S\r\n]+|[\p{L}\p{M}\p{N}]+(?:['’][\p{L}\p{M}\p{N}]+)*|[^\s\p{L}\p{M}\p{N}]/gu` (each newline its own token, whitespace runs one token, punctuation single, apostrophe words whole, linear); common prefix/suffix trim; Myers O((N+M)·D) storing only the live V rows (memory O(D²)); caps `MAX_TOKENS = 5000` per side after trim and `MAX_D = 1000` → `{ kind: "too-large" }`; adjacent same-type ops coalesced; a whitespace-only equal run between two changes folded into them. Computed in `ReviewCard` via `useMemo` only when `!streaming && proposal !== null && original !== null`. The **original is a request-time snapshot** (`reworkRequest.original`): `sel.text` for a selection, the body at request time otherwise; for a whole-text rework a `.review-note` reads `Edited since this rewrite was requested — Replace text overwrites those edits.` when `body !== original` (informational; Replace stays enabled). Rejected: jsdiff (a new dependency — the owner may still choose it, R-17); an LCS table (O(N·M) memory); diffing the live body (re-diffs per keystroke and hides what Replace will overwrite).
- **D8 — Two views, one toggle.** Inline (default): the proposal with `<ins className="rv-ins">` / `<del className="rv-del">` marks, each carrying an sr-only `added: ` / `removed: ` prefix (`user-select: none`), in `.review-body`. The item editor's proposed-title half stays full-width under the body and is not diffed. Rejected: `aria-label` on `ins`/`del` (ARIA 1.2 prohibits naming those roles); `--danger` text for deletions (fails on the card fill in all palettes — deletions use `--mark-ink` + `line-through`, insertions `--ins-fill` + underline); a tab pattern or `<select>` for the toggle; independent or ratio-synced column scrolling.

Rejected: reading the `useDraftBackup` flush registry (a module-level registry, not React state — badges would not re-render); field-level marking (out of scope, §10).
