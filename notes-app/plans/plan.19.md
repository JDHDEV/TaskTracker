# Plan 19: Editor polish batch — blurred-selection highlight, `Close saved` tab button, wheel-scrolled tab strip

**Created:** 2026-09-27
**Status:** Implemented 2026-09-27 (Phase 0 included) — executor's automated smoke and the owner's remaining checklist steps all passed (§12); uncommitted, §10 decisions pending
**Planning Mode:** Subagent-Enhanced

**Summary**
- **Goal:** Keep a body selection visibly marked after the editor textarea loses focus, add a one-confirm `Close saved` button to every editor tab strip, and let the mouse wheel scroll the tab strip horizontally — for the single owner-user of worknotes.
- **Approach:** Frontend-only: reuse the plan-17 mirrored backdrop with a new blur-time capture (`blurSel`) behind a pure precedence helper; a pure `runCloseSaved` sequencer folded through the existing `closeTabs` reducer behind a third bar button; a pure wheel-delta mapper driven by a native non-passive `wheel` listener in the shared strip; plus a minimal mid-save dirty guard for a verifier-confirmed race that the new button would otherwise amplify.
- **Scope:** 19 implementation steps; 16 files (3 create, 13 modify) across 5 directories
- **Top risk:** The confirmed SEC-1 race (edits typed while a save is running end up marked clean with their backup deleted) is a scope addition the owner may strike from Phase 0 — without it, `Close saved` bulk-closes falsely clean tabs behind one generic confirm.
- **Diagram:** [plan.19.diagram.html](plan.19.diagram.html) (threshold met: 16 files across 5 directories)

**Model Routing:** test-writer → sonnet (high, R2 — baseline kept); frontend-specialist → opus (medium, R3 — raised one tier for the browser-behaviour and state-precedence questions); no routes discarded; architect, security-auditor, tech-lead, adversarial-verifier and the plan review ran on frontmatter defaults (not routed).

## 1. Overview

Three small requests on the surfaces plans 13–18 stabilised — the three structurally identical body editors (`src/components/Editor.tsx`, `PromptEditor.tsx`, `ScratchEditor.tsx`) with their shared selection-rework machinery, and the three tab strips rendered by one `src/components/EditorTabs.tsx`:

1. **Highlight persistence on focus loss.** Select text in the body, click outside (the AI bar, a tag, the title, the rail): the selection should stay visibly marked so a selection rework is predictable. Today the rework already acts on the remembered range — `selRef` survives blur ([Editor.tsx:254-262](../src/components/Editor.tsx#L254)) — but Chromium does not paint a textarea's selection while it is unfocused, so the user can no longer see what `Rework` will act on. **This item is visual, not functional** (tech lead, verifier); the plan says so to keep anyone from hunting a bug that is not there.
2. **`Close saved` button.** Close every tab that has no unsaved changes after **one** confirm. Plan 18's `Close all` deliberately deferred this variant (plan 18 D1: "not VS Code's separate *Close Saved*"). Note the requested behaviour departs from plan 18's rule that clean tabs close silently — the request asks for a confirm, so the confirm stays and the asymmetry is recorded (§5 D4, §10).
3. **Wheel scrolls the tab strip.** Rolling the mouse wheel over the horizontal-only tablist scrolls it sideways. Since plan 18 D9 the strip has no vertical overflow, so a wheel over it does nothing at all today; DESIGN.md even states "the wheel never nudges the strip" and plan 18's smoke step s1-2 asserts it — both are superseded on purpose.

Why now: the three items are independent, each extends machinery that already exists (`SelectionBackdrop` + `selectionSegments`, `planCloseAll` + `closeTabs`, the `.editor-tabs-bar`), and together they are one afternoon of frontend work with no Rust, IPC, `types.ts` or on-disk change (architect, confirmed by reading every dependency).

**Scope defaults adopted** (non-interactive run — recorded as assumptions A1–A3 in §10): item 1 applies to all three editors; item 2's "windows" are editor tabs and the button goes on all three strips; item 3 means the wheel's vertical delta (middle-button autoscroll-drag is out of scope).

## 2. Strategic Assessment

*(tech-lead, opus)*

- **Verdict: go, as one batch.** All three items are small, independent, and extensions of plan-17/18 machinery. The one correction is to item 1: nothing is lost functionally today — `selRef` is written only by `trackSelection` from the textarea's own `onSelect`/`onKeyUp`/`onMouseUp` ([Editor.tsx:1120-1122](../src/components/Editor.tsx#L1120)) and cleared only on edit, paste or insert; clicking the AI bar never clears it. Plan it as a visual change.
- **Abstractions to leverage:** the `<mark>` mirror (`SelectionBackdrop`, rendered only from the pure `selectionSegments`, so a stale range draws nothing); `planCloseAll(...).clean` ([closeAll.ts:38](../src/lib/closeAll.ts#L38)) which is exactly "not dirty, including empty never-saved drafts"; the `closeTabs` reducer; the optional-prop pattern (`onCloseAll`/`closeAllLabel`) on `EditorTabs`.
- **Abstractions to avoid:** turning the backdrop into a general overlay; routing item 2 through `runCloseAll` (its Q1/Q2/per-draft flow does not apply and it closes an all-clean strip silently); any per-owner wheel code (the strip is shared).
- **Riskiest parts.** Item 1: widening *when* the highlight shows — `highlightSel = confirmingSel ?? (proposal ? selectionRework : null)` ([Editor.tsx:827](../src/components/Editor.tsx#L827)) gains a third source that must hide on focus (or the mirror and the native selection paint twice), keep the `body-transparent` swap in step, and go stale safely; `selRef` is a ref, so a state twin is required in all three editors. Item 2: a third button crowds the bar (re-smoke plan 18's narrow-pane case). Item 3: React registers `wheel` as a **passive** root listener, so a React `onWheel` cannot `preventDefault` (facebook/react#19651, #22794) — a native `{ passive: false }` listener on the scroller ref is required.
- **Highest-level approach:** item 1 — show the existing mirror whenever the body is blurred with a valid range, hide on focus, precedence written once in a pure helper; item 2 — a pure `runCloseSaved` beside `runCloseAll`, folded through `closeTabs` under the same re-entry guard; item 3 — native listener + pure delta mapper inside `EditorTabs`.
- **What would change the verdict:** the owner reporting a real repro where a rework used the wrong text (none is known).

## 5. Design

### Approach

Frontend-only, pure-where-possible, mirroring plans 17 and 18:

- **Item 1** — each editor gains one state, `blurSel`, captured on textarea blur (after re-reading the live range) and cleared on focus; it becomes the third, lowest-precedence source for the existing `SelectionBackdrop` via a new pure `pickHighlight` in `selection.ts`. `clearSelection()` and the reseeds clear it. The verifier-confirmed `selRef` leaks (`applyDraft`, whole-body `Replace text`, `discardEdits`) get `clearSelection()` so the AI bar's selection mode, the mark and the range a rework sends can never disagree. No CSS change; `.body-hl-mark` is reused as-is.
- **Item 2** — `closeAll.ts` gains `planCloseSaved`, `closeSavedQuestion` and `runCloseSaved({ getTabs, confirm })` (one confirm, post-confirm re-validation, never more than counted); `EditorTabs` gains optional `onCloseSaved`/`closeSavedLabel` props and a `Close saved` button between `+` and `Close all`, `aria-disabled` when no tab is clean; the three owners add `requestCloseSaved()` under the shared `closingAllRef`, folding through `closeTabs`.
- **Item 3** — new pure `src/lib/tabWheel.ts` (`wheelToScrollLeft`) and, in `EditorTabs`, a ref on the `.editor-tabs` scroller with a native non-passive `wheel` listener that assigns `scrollLeft` and prevents default only when the helper returns a new position.
- **Phase 0 (D0, strikeable)** — an edit-sequence counter in each editor's `edit()` chokepoint; `save()` records it before its first await and skips `setDirty(false)` + `clearAfterSave()` when it moved.

### Architecture

```
src/lib/selection.ts ──pickHighlight──▶ Editor / PromptEditor / ScratchEditor ──▶ SelectionBackdrop (unchanged)
src/lib/closeAll.ts ──runCloseSaved──▶ App / PromptsPage / ScratchPage ──closeTabs──▶ src/lib/openTabs.ts (unchanged)
                                            │ onCloseSaved / closeSavedLabel
                                            ▼
src/lib/tabWheel.ts ──wheelToScrollLeft──▶ EditorTabs (Close saved button + wheel listener)
```

Nothing new crosses into `src-tauri`, `src/lib/api.ts` (existing `confirmDialog` only), `types.ts`, `session.ts` or the on-disk format. The diagram [plan.19.diagram.html](plan.19.diagram.html) shows the change map; the plan file is authoritative.

### Key Decisions

- **D0 — Mid-save guard = an edit-sequence counter, not a buffer diff and not a read-only textarea.** `editSeqRef` increments in `edit()` (every buffered field change already funnels through it); `save()` captures it before the first await and, on success, marks clean and clears the backup only if it is unchanged. A false "still dirty" (e.g. a title edit that the save actually re-read) is safe; a false "clean" loses data. Rejected: comparing the live body to the snapshot (misses the other fields); `readOnly` during saves (contradicts plan 17's editable-while-busy rule, F14). The draft-promotion reseed overwrite is **not** fixed here (§10).
- **D1 — `blurSel` is state, captured on blur, cleared on focus.** `onBlur` runs `trackSelection()` first, then `setBlurSel(captureSelection(selRef.current, body))`; `onFocus` sets null. Rejected: reading `document.activeElement` at render (nothing re-renders on focus change); CSS-only (`::selection` is not painted on blur, the Highlight API cannot target a textarea — plan 17 §3); a second backdrop for a new selection while a card is open (needs overlap handling).
- **D2 — Precedence written once: `pickHighlight(confirming, pending, blurred)` = `confirming ?? pending ?? blurred`.** The card's range is the splice target (plan 13 H4, plan 17 F5); the blurred range is a mirror of the native selection. The stale check stays in the editors as today. Rejected: blurred-wins (hides the splice target); inlining the `??` chain a third time in three files (untestable).
- **D3 — Reuse `.body-hl-mark` unchanged.** One mark, one meaning. Rejected: an inactive variant.
- **D4 — `Close saved` always asks, `Close all` over an all-clean strip does not.** The request specifies one confirm; recorded as an accepted asymmetry in DESIGN.md. Zero saved tabs → the button is `aria-disabled` and the owner returns without a dialog (R-5). Rejected: skipping the dialog when everything is clean (contradicts the request); reusing `runCloseAll` with a filter (no re-read, silent all-clean close).
- **D5 — Re-validate through an injected `getTabs`, and close only `confirmed ∩ still-saved-and-open`.** Never more tabs than the dialog counted (R-1); a tab that turned *clean* during the await is also not closed. Rejected: a one-time `tabs` snapshot (the plan-18 shape); a symmetric re-plan (could close a tab the user was not told about).
- **D6 — Confirm wording and kind.** `Close 3 saved tabs? 2 with unsaved changes stay open.` (singular forms: `Close 1 saved tab? 1 with unsaved changes stays open.`; all clean: `Close 3 saved tabs?`), buttons `Close saved` / `Cancel`, default `warning` kind like `Close all` Q1. Rejected: `kind: "info"` (the `api.ts` comment reserves it for the one non-destructive rework confirm; changing that is a separate call).
- **D7 — Button label `Close saved`, names `Close saved open items` / `… open prompts` / `… open scratch pads`, tooltip `Close tabs with no unsaved changes`, position `+`, `Close saved`, `Close all`.** Styled with the `.etab-closeall` recipe (shared selector list) plus the `.etab-nav` `aria-disabled` dimming. Enablement uses the **same predicate as `planCloseSaved`** (`!dirty && !isDraft`; `EditorTabDescriptor` gains `isDraft`), so the button is never enabled while the sequencer would find nothing to close (plan reviewer). Rejected: "Close clean"/"Close unchanged"; an icon-only button; hiding it at zero (layout shift); `disabled` (drops focus to `<body>`).
- **D8 — Shared `closingAllRef`.** Rejected: a second guard (the two bulk flows could interleave; Back/Forward's R-8 guard would miss one).
- **D9 — Wheel = native `{ passive: false }` listener on the `.editor-tabs` ref + pure `wheelToScrollLeft`.** Contract: `null` = let the browser handle it (no overflow, `ctrlKey`, `deltaY === 0`, `|deltaX| ≥ |deltaY|`, or already at that edge); a number = the new clamped `scrollLeft` (may be `0`). The listener prevents default only when a number comes back. `deltaMode` 1 → `× WHEEL_LINE_PX` (16), 2 → `× clientWidth` (both effectively unreachable in Chromium, which sends pixels, but handled). Rejected: React `onWheel` (passive at the root since React 17); `scrollBy({ behavior: "smooth" })`; listening on the whole bar (bigger target but two refs and wheel-over-`Close all` scrolling tabs — can be added later if wanted); always preventing default (would block a future vertical ancestor).

## 6. Implementation Steps

Work phase by phase; run `npx tsc --noEmit` and `npm test` after each phase. Line numbers are approximate (verify by reading). Comment new code with `// Plan 19 (Dn): …` like plans 17/18.

### Phase 0 — SEC-1 guard (D0; recommended — strike this phase only if the owner says plan 19 must stay strictly to the three items)

1. **`src/components/Editor.tsx`:** add `const editSeqRef = useRef(0);` beside `lastEditRef`; in `edit()` (~787-795) add `editSeqRef.current += 1;` next to `lastEditRef.current = Date.now();`. ### Post-release fix (1.2.3)

Owner report after 1.2.2: "if the app loads with items in the banner, a vertical scrollbar appears on the far right and the whole app can be scrolled away." Reproduced with an in-app probe: `document.scrollingElement.scrollHeight` was 1611 on a 683 px viewport while `body`/`#root` reported no overflow. The only box below the viewport was the plan-17 rail-row marker `span.sr-only` (", unsaved changes") — the visually-hidden recipe is `position: absolute`, and with no positioned ancestor its containing block was the document, so its static position (the dirty row's place in the *unscrolled* rail list) extended the document instead of the list's scroller. It surfaces on a load with restored drafts because that is when dirty rows exist immediately (the banner only pushes the list further down; the scrollbar stayed after dismissing it). Fix, CSS only: `.list` and `.editor` (the two scrollers that hold `.sr-only` spans) become `position: relative`, and `html, body { overflow: hidden }` guards the invariant that the shell never scrolls. Verified live (document no longer scrollable in the restore state; the list, strip and editor pane still scroll; the rows' accessible names still end in ", unsaved changes"). Shipped as 1.2.3.
