# Plan 18: Tab-strip and navigation batch — close all, overflow fix + scrollbar styling, back/forward history, scratch move-on-send, high-contrast palette

**Created:** 2026-09-26
**Status:** Implemented 2026-09-26, owner-smoked 2026-09-27 (reduced 12-step pass, all PASS after the §12 item 19 fix; uncommitted — see §12)
**Planning Mode:** Subagent-Enhanced

**Summary**
- **Goal:** Give the three editor tab strips (items, prompts, scratch pads) a Close all action, a clean horizontal-only scroller with a palette-aware thin scrollbar, and browser-style Back/Forward over previously viewed tabs; make a scratch-pad "send selection to…" a *move* (the text leaves the pad, undoable with Ctrl+Z); and add a sixth, VS Code-inspired dark high-contrast palette.
- **Approach:** Keep everything frontend-only and pure where possible — a `navHistory` algebra folded into the existing `openTabs` reducers, an injectable `runCloseAll` sequencer with one aggregate confirm instead of two dialogs per tab, CSS-only strip fixes using the standard `scrollbar-*` properties, a native `execCommand("delete")` cut in the scratch editor, and a sixth `data-palette` token block guarded by a test that reads `styles.css`.
- **Scope:** 24 implementation steps; 20 files (7 create, 13 modify) across 8 directories
- **Top risk:** Back/Forward is the most speculative item — its keyboard chord (Alt+Left/Right) and mouse-button path can only be verified in the running WebView2 (whether `preventDefault` beats the browser accelerator is unverified), and the pruning semantics ("Back never reopens a closed tab") is a recorded default the owner may want reversed. Its ‹ › buttons ship in Phase 3 alongside Close all (same files), but its model (steps 3–5 history parts) and its shortcut hook (step 11, the last wiring in Phase 3) are separable, so the keyboard/mouse path can be dropped without affecting the other five items.
- **Diagram:** [plan.18.diagram.html](plan.18.diagram.html) (threshold met: 20 files across 8 directories; new cross-module edges `openTabs.ts → navHistory.ts`, owners → `closeAll.ts` / `useBackForwardKeys.ts`, `stylesGuard.test.ts → styles.css`; Phase 2 must land before Phases 3–4)

**Model Routing:** test-writer → opus (confidence medium, matched_rule R3); frontend-specialist → opus (confidence medium, matched_rule R3); no routes discarded, no injection suspected. tech-lead, architect, security-auditor, adversarial-verifier and code-reviewer ran on their frontmatter defaults (routing never covers them); no database-architect, api-designer, devops-engineer or performance-optimizer was spawned (no schema, API, CI or hot-path signal in the feature).

## 1. Overview

Six owner requests, all on the editor-tab surface that plans 11–17 built (`src/lib/openTabs.ts`, `src/components/EditorTabs.tsx`, the three tab owners `src/App.tsx` / `src/components/PromptsPage.tsx` / `src/components/ScratchPage.tsx`), plus the scratch pad's send-to path and the palette system:

1. **Close all tabs** — one action that closes every open tab in the strip, saved and unsaved alike, with a sane confirm for unsaved work (today each tab must be closed one at a time, two native dialogs per dirty tab).
2. **Fix tab overflow scrolling** — the strip shows an unwanted *vertical* scrollbar (and wheel-scrolls 1px vertically); only horizontal scrolling should exist.
3. **Style the horizontal scrollbar** — the strip's native scrollbar is the OS light default in every palette; give it a thin, palette-aware look.
4. **Back / Forward navigation** — ‹ › buttons (plus Alt+Left/Right and the mouse back/forward buttons) that walk the history of previously viewed tabs, browser-style.
5. **Remove the selection after moving it from the scratch pad** — "New note/task/prompt from selection" currently *copies* (plan 13 D5); it should *move*: the text leaves the pad.
6. **High-contrast VS Code-style palette** — a sixth palette with black backgrounds, white text and VS Code Dark High Contrast's cyan/orange accents for readability.

Why it matters: the tab strip is now the app's primary navigation and it has three visible rough edges (stray scrollbar, unstyled scrollbar, no bulk close); Back/Forward is the missing piece once several tabs are open; the copy-not-cut send leaves duplicated text the user must clean up by hand; and none of the five palettes is high-contrast for low-vision use. The whole batch is frontend-only: no IPC, no Rust, no on-disk format change (confirmed by the architect — the palette id lives only in localStorage, where an older build's whitelist falls back to Original).

## 2. Strategic Assessment

Source: tech-lead agent (opus), read-only. Verdict: **proceed, with changes**, landing lowest-risk first and Back/Forward last (droppable).

- **Bundling six items is fine** — they are small, all frontend, and each becomes its own phase with its own acceptance criteria so any one can be cut.
- **Landing order:** (1) overflow fix + scrollbar styling as one CSS phase, (2) pure model, (3) strip UI + wiring, (4) scratch move, (5) high-contrast palette, (6) docs. Back/Forward's UI rides Phase 3 but its shortcut hook is the last thing wired.
- **Abstractions to leverage:** the generic, pure, node-tested `openTabs.ts` reducer (`closeTab` at [openTabs.ts:105-114](../src/lib/openTabs.ts#L105)); `EditorTabs`' optional-prop pattern (`onNew?`, [EditorTabs.tsx:22-24](../src/components/EditorTabs.tsx#L22)) for plugging in Close all and ‹ ›; the palette whitelist-with-fallback ([palettes.ts:41-55](../src/lib/palettes.ts#L41)) which makes a sixth id safe against stale stored values; `insertText(body, range, "")` in [timestamp.ts:29-41](../src/lib/timestamp.ts#L29), which already performs a range delete; the existing focus-after-close logic ([EditorTabs.tsx:53-63](../src/components/EditorTabs.tsx#L53)), which keys off actual key removal so a bulk close restores focus with no extra work.
- **Abstractions to avoid:** the native context menu for Close all (drags in Rust for no gain); `::-webkit-scrollbar` (Chromium 121+ ignores it once the standard properties are set); adding the history to every activation call site (drifts as new paths appear).
- **Riskiest parts:** (a) Close all with many dirty tabs becomes a dialog storm if the per-tab flow is looped (two chained Yes/No dialogs per tab, [App.tsx:763-780](../src/App.tsx#L763)) → use one aggregate flow; (b) Back/Forward has the most complexity for the least certain value — pruned history is close to an MRU switcher, and WebView2 may intercept Alt+Left; (c) the scratch move reverses recorded decision plan 13 D5 ("copy, not cut" — [plan.13.md:28](plan.13.md), [:149](plan.13.md)); the coupling objection that led to D5 does not apply to an *immediate* cut, but the app has no undo, so the removal must be recoverable; (d) the sixth palette can silently miss one of the six name-enumerated dark-override selector groups in `styles.css` — a stylesheet guard test closes that hole; (e) the overflow fix is not a bare `overflow-y: hidden` — the active tab's 1px join with the editor must be drawn a different way.
- **Assumption changes adopted from the tech lead:** A1 (per-tab confirm chain → aggregate flow), A2 (bare `overflow-y: hidden` → preserve the join), A3 (history mechanism must not be wired into each activation site). The architect and frontend specialist subsequently refined A3 further (history lives *inside* the reducer state, see §5), and refined the scrollbar and cut mechanisms.

### 3.2 Frontend specialist (opus, routed) — measured facts and design inputs

- **WebView2 runtime is Chromium 153** (measured via the EdgeUpdate registry key: `pv 153.0.4234.48`). Past 121, so once `scrollbar-width` / `scrollbar-color` are set on an element Chromium ignores its `::-webkit-scrollbar*` rules — write only the standard properties.
- **Vertical scrollbar root cause (confirmed):** `overflow-x: auto` on `.editor-tabs` ([styles.css:673-682](../src/styles.css#L673)) makes `overflow-y` compute to `auto`; with `align-items: flex-end` and `padding-bottom: 0`, `.etab-on { margin-bottom: -1px }` ([styles.css:700](../src/styles.css#L700)) ends the active tab's border box 1px below the padding box → 1px of vertical scrollable overflow → vertical scrollbar, and the wheel scrolls the strip 1px. **Corollary refined:** a scroll container clips at its *padding* box and paints its own border outside the clip, so the active tab's overhanging 1px is clipped *today* and the strip's `border-bottom` already shows under the active tab. A bare `overflow-y: hidden` changes nothing visually; restoring the join needs the hairline drawn *inside* the padding box (inset `box-shadow`) with 1px of bottom padding for the active tab to overlap. Strip height stays 41px.
- **`color-scheme` is not declared anywhere**, so native scrollbars and form controls render light in the dark palettes — an app-wide follow-up, out of scope (adding `color-scheme: dark` would double-invert the date-picker glyph already inverted at `styles.css:1555` and restyle `<select>` popups).
- **Scrollbar thumb colour:** `--muted` over a transparent track passes 3:1 against `--bg` in every palette (Original 4.20, v2-light 3.06, v2-dark 5.14, neon-noir 6.08, claude-terminal 4.78, hc-dark 12.55); `--line` and `--outer` do not (1.15–1.85). `scrollbar-gutter` reserves only the *inline-axis* gutter and cannot stop the strip growing by the horizontal scrollbar's thickness when overflow starts — accepted (a thin bar makes the jump small).
- **`--surround` and `--outer` are declared but unused** by any rule (grep: no `var(--surround)` / `var(--outer)`); set them in the new block for completeness only.
- **Controls in a tablist:** the `+` button already sits inside `role="tablist"` (a minor 4.1.2 issue); new controls go in a wrapper *outside* the tablist. Use `aria-disabled="true"` + no-op (not `disabled`) at the ends of history so repeated presses never drop focus to `<body>`. Alt+Left/Right bind no textarea editing command on Windows (word movement is Ctrl+Arrow), so no editing clash beyond the two arrow handlers above. Chromium navigates on `mouseup` of buttons 3/4 and `preventDefault()` there cancels it. `.etab-x` (20×20, [styles.css:719-725](../src/styles.css#L719)) is under the 24×24 target minimum; new controls should match `.etab-new` (30×30). The tab focus ring reaches 3px below the tab and is clipped by the strip — `.etab:focus-visible { outline-offset: -2px }` avoids it.
- **High-contrast token set and ratios** — see §5 Key Decisions D7; five base rules fail with HC tokens unless their per-palette groups gain the id (`.etab-x` ink on `--line` 1.99:1; `.etab-x:hover`, `.review-mark`, `.btn-save` `--mark-ink` on `--mark` 1.63:1; `.page-tab-badge` 2.57:1) — all fixed by the literal `#000000` ink the dark groups already use (8.18:1 on `#f38518`). Status dots on black: doing 9.34, testing 5.10, done 5.13 (all pass 3:1 non-text; `--done` used as *text* clears 4.5:1 only narrowly — AA, not 7:1).
- **Cut mechanism:** `document.execCommand("delete")` on the still-focused textarea fires `input`, so the existing `onChange` → `edit()` + `clearSelection()` path runs, React sees the DOM value already equal to state and does not rewrite `value`, and the native undo stack survives — Ctrl+Z restores the text. Remove *before* `onSendTo`, because `onSendTo` hides the pad and moves focus in the same batch.

## 5. Design

### Approach

Everything stays in the frontend and, wherever behaviour can be expressed without React, in pure `src/lib` modules the node vitest harness can pin:

- **Tab strip (items 2–3):** CSS-only on `.editor-tabs` — restore the active-tab join with an inset-shadow hairline and 1px bottom padding, `overflow-y: hidden` as a safety net, and the standard `scrollbar-width: thin` / `scrollbar-color` driven by tokens (no `::-webkit-scrollbar`, no `scrollbar-gutter`).
- **Close all (item 1):** a pure `closeTabs(state, keys)` reducer plus an injectable `runCloseAll` sequencer in `src/lib/closeAll.ts` (confirm, save, discard and activate are passed in, so the dialog branching is unit-tested with fakes). Aggregate flow: clean tabs close silently; if anything is dirty, **Q1** "Close all N tabs? M have unsaved changes." (Cancel = nothing changes) then, for dirty *saved* tabs, **Q2** "Save the M unsaved tabs before closing? Yes saves and closes; No discards them." A failed save keeps that tab open; never-saved drafts are activated one by one and get the existing "Discard this unsaved …?" confirm (keep = stays open). The control is an optional `onCloseAll` prop on `EditorTabs`, rendered outside the tablist.
- **Back/Forward (item 4):** a pure `NavHistory { entries, index }` algebra in `src/lib/navHistory.ts`, carried as a `history` field of `OpenTabsState` and maintained *by the reducers* (`openTab`/`activateTab` visit, `closeTab`/`closeTabs` prune and re-visit the neighbour, `promoteTab` renames, new `navigateTab` moves without visiting, `resetHistory` after session restore). Invariant: every entry is an open tab key and `entries[index] === activeKey` whenever tabs are non-empty; Back never reopens a closed tab (v1). ‹ › buttons live in the strip's wrapper bar; one `useBackForwardKeys` hook per owner handles Alt+Left/Right and mouse buttons 3/4, gated on the visible page. Nothing is persisted.
- **Scratch move (item 5):** in the same context-menu handler, capture → `execCommand("delete")` while the pad is still focused (native undo survives; the existing `onChange` → `edit()` path marks dirty and feeds the draft backup) → `onSendTo`. Fallback to `insertText(ta.value, sel, "")` + `edit()` with a *non-focusing* caret if `execCommand` returns false. A toast discloses the move. `scratch.md` on disk is untouched until the pad's explicit Save.
- **High-contrast palette (item 6):** one dark palette `hc-dark` ("High contrast (VS Code)") — a sixth token block modeled on VS Code Dark High Contrast plus the sixth selector in each of the six dark-override groups, an HC-only `.etab-x` override, and a stylesheet guard test that fails when any dark palette is missing from any dark group.

### Key Decisions

- **D1 — Close all is a shared `EditorTabs` control outside the tablist, per strip.** Rejected: a native context-menu item (Rust change), a per-page rail button, a cross-page "close everything" (each page owns its own confirm flow and editor handles; R-5). "All open and saved tabs" is read as *close everything, clean tabs included* — not VS Code's separate "Close Saved". Recorded default.
- **D2 — Aggregate consent, extracted and injectable.** Rejected: looping the per-tab flow (2 dialogs × N — the tech lead's "dialog storm"); one-shot discard-all (silent loss of never-saved drafts, which exist only as a buffer + backup). Chosen: Q1 (Cancel = no change) → Q2 Save/Discard for dirty saved tabs → per-draft Discard confirm. Drafts are **never bulk-destroyed** and are **never bulk-saved** (a draft save may need a target project and fires an AI title call — [Editor.tsx:223](../src/components/Editor.tsx#L223)). Trade-off: "Close all" can leave a kept draft or a failed-save tab open; the owner reports what stayed open with a keyed toast.
- **D3 — History lives inside `OpenTabsState`, maintained by the reducers** (architect + frontend specialist; the tech lead's watcher-hook alternative was rejected). A hook diffing `activeKey` would record close-driven neighbour activations and boot restore as visits, leave `draft-<uuid>` keys dangling after promotion, need a "navigating" ref flag, and double-push under StrictMode; it is also untestable without jsdom. Adding the field is safe: state is only ever built by `emptyTabs()` + reducers and no test compares whole state objects.
- **D4 — Closing the active tab re-visits its neighbour.** After `prune`, the clamped index can land on an entry that is *not* the neighbour `closeTab` activated (e.g. tabs [a,b,c,d], visits d,a,c, close c → neighbour d but the clamp lands on a). So `closeTab`/`closeTabs` prune and then `visit(neighbourKey)`, keeping `entries[index] === activeKey`; consecutive-duplicate collapse makes it a no-op when the clamp already agrees.
- **D5 — Back never reopens a closed tab (prune), per strip, not across pages.** Rejected: reopen-on-back (needs cached snapshots of possibly deleted/unloaded entities and an `api.getItem` round-trip — its own plan), app-global `{page, key}` history (needs an imperative "activate key" channel into `PromptsPage`/`ScratchPage`, about twice the wiring). Trade-off: after a scratch send, Back on Worknotes goes to the previous *item*, not the pad; the per-strip placement makes the scope visible.
- **D6 — Scratch move: immediate native cut, before `onSendTo`, disclosed by a toast — supersedes plan 13 D5.** D5's objection was the cross-page lifecycle coupling of "remove on the destination's Save"; an immediate cut has no coupling. Rejected: cut-on-destination-save (an unpersistable draftKey→{pad, range} correlation, stale-range semantics, ~5× the code); a pure `edit()` cut as the primary path (loses native undo — a *destructive* edit deserves Ctrl+Z even though Insert timestamp accepts the state path for an additive one). The Rust labels stay "New … from selection"; the toast says "moved". Recovery paths: Ctrl+Z in the pad; the unsaved pad (`scratch.md` keeps the text until Save); the destination draft.
- **D7 — `hc-dark` palette, dark polarity, tokens modeled on VS Code Dark High Contrast; status dots stay constant.** Values (frontend specialist, WCAG ratios computed): `--bg #000000`, `--surface #0f0f0f`, `--ink #ffffff` (21:1), `--muted #c8c8c8` (12.55:1 on bg), `--line #6fc3df` (contrastBorder; 10.55:1 non-text vs bg), `--surround #000000`, `--outer #6fc3df`, `--mark #f38518` (activeContrastBorder; 8.18:1 vs bg), `--mark-soft #2e1a05`, `--mark-ink #ffc285` (10.51:1 on mark-soft), `--danger #f48771` (8.55:1), `--todo #c8c8c8`, `--doing/--testing/--done` unchanged, `--hl-fill: color-mix(in srgb, var(--mark) 25%, var(--surface))`. The dark groups' literal ink on `--mark` is `#000000` (8.18:1). `.btn` fill: `#000` with a `--line` border, hover `#1a1a1a`. Rejected: an `--on-mark` token refactor collapsing the six groups (right long-term, wrong batch — touches every palette's rendering); a light HC variant (out of scope; the id leaves room for `hc-light`). Honesty note: bg vs surface is 1.10:1, so regions are told apart by the bright `--line` — every hairline turns cyan, loud but honest; the modal scrim (`--scrim`, constant) is nearly invisible on black and dialogs rely on their `--line` border. This is an "HC-inspired palette", not Windows forced-colors support.
- **D8 — Standard `scrollbar-width` / `scrollbar-color`, scoped to `.editor-tabs`** (tech lead + frontend specialist; the architect's `::-webkit-scrollbar` recommendation was rejected because Chromium ≥121 — measured 153 — ignores the pseudo-elements once the standard properties are set, and the only-webkit route gives up the standards-track properties). Trade-off: no thumb radius or thumb-level hover; the affordance is a discrete `scrollbar-color` swap on the container's `:hover`. App-wide scrollbars untouched; `color-scheme` follow-up recorded.

**Verifier addendum (adversarial-verifier, fable):** both claims **CONFIRMED**, high confidence, by a headless Chrome 153 reproduction built in the scratchpad from the verbatim rules (the WebView2 runtime is the same Blink 153 generation). Root cause: `overflow-y` computes to `auto`, `.etab-on.bottom` sits 1px past the padding box, `scrollHeight − clientHeight === 1`, a 15px classic vertical scrollbar appears; under forced horizontal overflow both scrollbars appear. Corollary: with a bare `overflow-y: hidden` the bar goes but the 1px is still clipped, and in the as-is build the hairline already runs unbroken under the active tab (the join has never rendered). The verifier measured the D9 fix (`padding: 4px 12px 1px; border-bottom: none; box-shadow: inset 0 -1px 0 var(--line)`, `.etab-on` margin kept): `vOverflow = 0`, no vertical scrollbar, strip height unchanged at 41px, non-active tabs 1px above the line, join rendering; under horizontal overflow only the horizontal scrollbar appears. Two notes adopted into step 1: do **not** remove the `-1px` margin instead (every tab would then cover the line); and when a classic horizontal scrollbar is present Chromium paints the inset shadow beneath it, so no hairline separates the scrollbar from the editor in that state — accepted as cosmetic. Alternative causes (`.etab-new`'s `align-self`/margin, the 2px transparent border-top, `.pin`'s rotation, `min-height`, `scrollbar-gutter`) were tested and excluded. Side effect to disclose: a `chrome.exe --version` probe without `--headless` may have opened a blank tab in the owner's running Chrome.
